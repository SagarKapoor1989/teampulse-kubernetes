# 3. Benefits, Challenges and Security

TeamPulse’s microservice architecture splits browser access, task handling, statistics and data storage into parts. This makes each part easier to understand easier to maintain easier to deploy and easier to scale on its own. For example the Insights part can get copies without having to add more copies of Tasks or Web. The custom services have no stored state while Redis keeps data persistently. Because of that Kubernetes can swap pods without losing any work. Separate services also give a bit of protection if one part fails.

The main challenges are complicated deployment, network lag, dependencies between services and having only one Redis instance. Docker Compose, repeatable Kubernetes files, health checks, timeouts and limits on resources all help lessen these problems. Kubernetes will restart services that fail and the Redis persistent volume keeps data safe. In a production system one could add Redis replication, backups, circuit breakers and monitoring. Because TeamPulse is small this design is mostly shown to prove that parts can scale separately.

Only the Web part is open to the public. NetworkPolicies control which services can talk to each other and only the Tasks part gets Redis credentials, from a Kubernetes Secret. All inputs and the size of each request are checked for safety. The containers run without root privileges with capabilities removed use read‑only file systems and set security headers. The demo does not have login, authorization or HTTPS. In production one should add TLS, OIDC, role‑based access, rate limits, audit logs, an external secret manager, image scanning and verified database backups.
